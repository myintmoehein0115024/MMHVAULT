## Draft-only MFA async stale-response guard (2026-11-01)
- Reviewed Account Security's MFA setup/confirm promises, modal collapse, sign-out and user-switch callbacks. A delayed `auth.mfa.enroll()` response could otherwise render a TOTP QR after its modal was closed, or after a different account signed in.
- Draft-only security-center fix commit `6dc77d16fff22d6e95f423c0434b1cb9f8925b00` introduces `mfaEpoch` and `mfaFlowActive(epoch,userId)` (same owner, same epoch, foreground tab, visible modal). `clearMfa` invalidates pending MFA requests synchronously; delayed enrollment results are never rendered, and orphan unenrollment is attempted **only** if the current independently authenticated user is still the same owner. Unsuccessful cleanup is intentionally not called a verified removal.
- MFA verification must also pass the epoch/modal/owner check after challenge, server verification, AAL2 read and verified-factor inventory read before a success message. A verification already completed on the server cannot be reverted merely by hiding the UI; server-side factor state remains the authority.
- On `SIGNED_OUT` or `SIGNED_IN` with a different UID, recovery words, QR/setup secret and sensitive UI state are cleared **synchronously**, irrespective of the `busy` flag. Deferred `refresh()` cannot be relied on to clear secrets.
- The dedicated synthetic UI regression `test-ui-secret-guards.mjs` verifies stale epoch, switched UID, hidden tab, hidden modal and final success ordering. Fix to legacy test expectation and new assertions commit `9c641374990798733726a975ea519912c339766d`. GitHub Actions run `41231983225` **SUCCESS**, **15/15 UI secret-guard checks**. These are offline source and synthetic behavior tests, **not** a signed browser session or production acceptance.
