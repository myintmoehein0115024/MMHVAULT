## 核验条件

部署前必须确认项目 ID、健康状态、无同名对象以及正式 `main` SHA 不变，GitHub CI 通过。部署后 SELECT pg_catalog 验证：

1. 仅 2 张目标新表存在，均启用 RLS，`anon`/`authenticated` 无读写权限。
2. 唯一性 `username_key` 为 PK、`user_id` UNIQUE FK，目标 RPC 为 SECURITY INVOKER。
3. `authenticated` 与 `anon` 无 RPC EXECUTE，服务端角色有 EXECUTE。
4. 新表为空，无真实用户名或用户资料。
5. Edge slug 存在，`verify_jwt=true`，源码仍有 1970 关窗和 `CODE_GATE_OPEN=false`。
6. 生产既有 Edge、正式 `main` 和生产 59 张原有 public 表安全状态不得因发布发生变化。

## 回滚策略

- **首要停用操作**：保持 `CODE_GATE_OPEN=false`、平台 `verify_jwt=true`，必要时重新部署仅返回 `503 disabled` 的安全关闭版本；当前工具不具备直接删除 Edge 的连接操作，彻底删除需另行通过 Supabase Dashboard/受权限工具审查完成，不能假称自动删除成功。
- **表/函数处理**：运行纯 SELECT 检查两张表的行数。只允许对这次**新建且确定没有数据**的对象规划删除；若任何表有行、存在真实账户绑定或有新依赖，则**停止删除**并另行评估/备份，不得直接清空用户名映射以免账户失去登录别名。
- **若另外获得授权执行结构回滚**：先执行 `DROP FUNCTION public.mmh_n10a740_take_attempt(text,integer,integer)`，再分别执行 `DROP TABLE public.mmh_n10a740_attempt_buckets`、`DROP TABLE public.mmh_n10a740_username_links`。禁止 `CASCADE`，避免误触及既有对象。应用记录在 Supabase migration history 中，必须留存，不得擅自删除其他 migration。
- **无需对旧财务数据做回滚**：本次完全未接触旧表。既有数据库/项目/Edge 绝不恢复快照或整体回退，以免覆盖在此期间产生的用户交易。
